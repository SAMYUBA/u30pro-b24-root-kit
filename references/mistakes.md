# 错题本

这里记录实际遇到的现象与证据边界。避免用更多刷写替代诊断。

| 现象或错误假设 | 实际发现 | 下次怎么做 |
| --- | --- | --- |
| sandbox 内看不到 USB，于是认为设备没接好 | 提升到具备 USB 访问权限的本机检查后可见 | 区分执行环境权限、线缆、供电和设备模式；先查枚举再动固件 |
| 某个 VID/PID 出现就说明 ADB 打开 | 同一 PID 可对应 NCM + MTP，或额外包含 ADB | 检查 ADB 接口 `ff/42/01`、端点和 `adb devices` |
| 首页正常，但没有 ADB，所以 Root 失败 | 启动观察器记录 root 身份、Magisk 进程和成功的 `su` | 将启动、内部 Root、USB 暴露和主机授权拆开验证 |
| `adbd=running` 就表示 Mac 可以获得 shell | 设备曾短暂运行 adbd，随后 USB ADB 被移除 | 同时检查 USB functions、FFS readiness、服务状态和主机端会话 |
| 把启用 ADB 放在 Magisk 等待之后 | 等待扩大启动时序的不确定性；调整顺序后仍未解决全部问题 | 记录每个阶段的时间；不要把先后顺序调整当作已证明根因 |
| 仅写 `sys.usb.config=ncm,mtp,adb` 即可保持 ADB | 启动后约数秒回到 `ncm,mtp`，adbd 停止 | 检查框架设置及后续状态，不循环强制重写 USB |
| `settings put global adb_enabled 1` 一定解决 | 本次写入从 0 变 1，但第一次重启观察仍出现回退；之后的全局值当时未测量 | 区分立即读回与数分钟后的值；不宣称已确定是谁重置设置 |
| 改 RNDIS 后成功，故根因一定是 NCM | 修改前已有启动脚本、全局设置等变化；成功时接口实际是 NCM + MTP + ADB | 报告完整成功序列和混杂变量，后续用受控比较验证因果 |
| 没拿到 SMB 日志就证明脚本未运行 | 重启会断开共享，路径、挂载状态和写权限也会影响报告 | 先核对网络和共享挂载；用受限路径回退和本地随机标记 |
| 同一报告里的所有 snapshot 都属于本次启动 | 报告跨启动追加，编号重新开始，尾部可能正在写 | 按启动边界、进程与前后文区分；保留读取时间，不混算样本 |
| 等待启动时 ADB 窗口即可免刷修复 | 有限时间监听没有捕获可授权会话，未执行远端命令 | 明确记录“未连接、未修改”；不把超时当成执行成功 |
| 原厂签名块还在，修改镜像就仍获签名 | 签名 blob 可保持有效，但 body 已变，descriptor 不再匹配 | 分别验证签名、descriptor 和实际启动机制；说明 TrustOS 路线依赖 |
| 多份 NV 文件就足以保证恢复 | 长会话存在不一致，冷启动重复读取一致；全恢复未演练 | 保留不一致证据，说明恢复局限，不覆盖旧副本 |
| restore init_boot 等于完全恢复原厂 | TrustOS 和持久化 `adb_enabled` 可能仍是修改后的值 | 按每个已变更项列恢复范围，不承诺“一键回原厂” |
| 下载包内所有文件都可以发 GitHub | 公共下载不等于开源许可，备份和公钥也可能关联设备/用户 | 只发布自编代码与脱敏说明，通过链接获取第三方依赖 |

## 调试顺序

1. 电源、连接、执行环境权限与 USB 枚举。
2. 首页、启动完成、槽位与基础网络。
3. 镜像静态完整性、写后读回与 Magisk 内部运行证据。
4. USB 接口、adbd、授权和 Android 框架状态。
5. 最小变量实验及重复验收。

不要把其他 ZTE 型号的 ubus 命令、不同固件的工程接口或 TCP ADB 模块直接用于 B24。本案例没有找到可直接证明相同硬件、B24 和 macOS 故障根因的社区成功案例。

框架机制参考：[AOSP UsbDeviceManager](https://github.com/aosp-mirror/platform_frameworks_base/blob/android-15.0.0_r1/services/usb/java/com/android/server/usb/UsbDeviceManager.java)。它能解释一种撤销 ADB function 的机制，不能识别本机 OEM 回写的具体调用者。
